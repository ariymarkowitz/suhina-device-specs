# CC Control (manual 30.2)

**Family:** control
**Note status:** dump checked, partly measured (MIDI recordings, [Measured](#measured))

## Summary

A device that creates MIDI control messages: three fixed controls (Mod Wheel, Pitch Bend,
Pressure) and thirteen custom controls (Custom A is a button meant for the sustain pedal, Custom
B to M are dials) whose controller number is chosen per control, so that a Live set can drive
the parameters of external hardware or of a plug-in by CC, and so that the values can be
automated or recorded into MIDI clip envelopes [manual]. The sixteen controls show in two pages
of eight, a Send button emits every current value, and a Learn mode assigns an incoming CC to a
control [manual]. It is new as a built-in device in Live 12.0 [source: 2].

Shared parts: [common.md](common.md) (title bar, racks, non-note messages). This device has no
Scale Awareness, no tempo sync and no note processing.

## MIDI flow

```text
                      ┌──────────── incoming MIDI (notes, CCs, pitch bend, pressure …) ──────────────┐
                      │                                                                               ▼
 16 controls ─► value changed? ──► CC / pitch bend / pressure message ──► merged with ──────────► output
 (dial moves,    (knob, automation,   (7-bit 0–127, or 14-bit pitch bend)   CC automation of the
  automation,     clip envelope,                                           same message on the clip
  Send, Learn)    macro)                                                   [manual]
```

1. **Controls** produce a message when their value changes: moving a dial or button, automation
   of the control, a clip envelope, a Rack macro mapped to it [manual; inferred].
2. **Send** emits the current value of every control at once [manual].
3. **Learn** listens to the incoming MIDI of the track and sets the selected custom control's CC
   Type to the number of the first CC it receives [manual; source: 2].
4. **Merge.** If CC automation for the same message exists (a clip envelope of the clip that is
   playing), the automation's data and the device's data are merged into one stream [manual].
5. Notes at the input pass through unchanged: 16 notes (pitch, start, length, velocity, release
   velocity) came out equal to the input with the device on and with controls stepped by
   automation [measured 12.4.6]. Other messages at the input: [inferred; measure, common.md
   case C7]. The device is not a filter.

## Controls

16 controls, in two pages of eight. The title bar has the two page toggles ("1–8" and "9–16"),
**Send** and **Learn**. The order on the pages is the manual's order: Mod Wheel, Pitch Bend,
Pressure, Custom A, then Custom B to M, which makes controls 1 to 3 the fixed ones, 4 the
button and 5 to 16 the twelve dials (the manual states the groups and the pages, not which
control sits on which page) [manual; inferred]. The Live API lists the parameters in that
order too: Device On, Mod Wheel, Pitch Bend, Pressure, Custom A, Custom B … Custom M
[dump 12.4.6]. Ranges, defaults and displays are from the Live 12.4.6 parameter dump of a device
freshly loaded from the browser [dump 12.4.6]; loaded and reset values agree for every
parameter. The page toggles, Send, Learn, the CC Type choosers and the names are not API
parameters.

## Behaviour

- **What triggers a message.** A message is sent when a control's value changes (a dial moved by
  the mouse or a controller, a button toggled, automation, a clip envelope, a Rack macro) and
  when Send is pressed [manual; inferred]. Because MIDI CC values are integers, a continuous
  automation ramp sends only each new integer value, not every audio block [inferred]; whether
  repeated equal values are suppressed is [measure].
- **Initial values.** Whether loading the device or opening the set sends the controls' values
  (the firmware of a hardware synth can then jump) is not stated; this is why Send exists, and
  12.4's MPE Control stopped sending its initial CC 74 [source: 2], which suggests a device that
  does not [measure].
- **Value and message mapping.**
  - Mod Wheel: CC 1, 7 bit [inferred]. If the target synth uses the 14-bit MSB/LSB pair
    (CC 1 and CC 33) is [measure].
  - Pitch Bend: 14-bit message, a centred value at 0 [inferred; measure].
  - Pressure: channel pressure, 7 bit [manual; inferred].
  - Custom controls: the CC chosen in the CC Type chooser, value = the control's position
    scaled to 0 – 127 [inferred].
  - Custom A: 127 when on and 0 when off for CC 64 [inferred]; for other assignments "on/off or
    minimum/maximum" [manual].
- **Output channel.** The channel is the one the track outputs: the incoming events keep
  theirs, and generated messages use the track's output channel or channel 1 [inferred;
  measure]. The device has no channel control in the manual.
- **Merging with automation.** If the playing clip has a CC envelope for the same message
  (the Mod Wheel envelope in a clip, for instance), the data from the clip and the device's data
  are combined into one output [manual]. How (last value wins, both are interleaved in time, the
  device's value is added to the clip's) is [measure].
- **Learn.** With Learn on, the first CC (any CC? from the track's input) that arrives selects the
  CC Type of the selected custom control; the dial can then be moved by the controller
  [manual; source: 2]. Whether Learn consumes the CC (it does not reach the output), moves
  the dial to the incoming value at once, and which control is "selected" when none was clicked,
  are [measure]. Learn does not apply to the three fixed controls [manual: it assigns to "a
  customizable control"].
- **Rack macros and automation.** The 16 controls are normal automatable parameters, can be
  mapped to Rack macros and appear as clip envelopes; they also appear on Push [manual;
  inferred].
- **Latency.** None reported; the device is stateless apart from the held values [inferred].
- **Presets.** The names, assignments and values are saved with the preset [manual].

## Edge cases

- **Two controls with the same CC Type.** Both send; the last change wins at the receiver
  [inferred; measure].
- **A CC Type that is also arriving at the input** (the controller sends CC 7 and Custom B sends
  CC 7): merged in time at the output [inferred; measure].
- **Device switched off.** Output stops; held values are not reset (a hardware synth keeps
  its last value) [inferred; measure, common.md C1]. A sustain pedal (Custom A) left on at
  switch-off is not released unless a message is sent [measure].
- **Transport stop and loop jump.** No state tied to the transport [inferred]; clip envelopes
  are played by the clip engine and merged [manual].
- **Automation of a control while it is being merged with a clip envelope**: see Merging.
- **Learn while a note is playing**: unaffected.
- **Values at the ends**: 0 and 127 exactly; Pitch Bend's −64 and +64 [dump 12.4.6] as
  −8192 and +8191 (or ±8192 clipped) [measure].
- **Sluggish dials** were a 12.0 problem fixed in 12.0.5 [source: 2]; not behaviour.

## Measurement plan

Method: common.md › Measurement plan, way 1. Record the output of a MIDI track holding the
device on a second armed MIDI track; read the messages. A clip's note list does not show CCs,
so the recorded **clip envelopes** (Mod Wheel, Pitch Bend, Pressure and the clip's MIDI Ctrl
lanes) are the read-back: the Remote Script reads notes only (`get_clip_notes`), so the envelopes
need the UI or a saved `.als` of the recording [measure]. An alternative that fits the
harness: send the track to a **MIDI Monitor** (Max for Live MIDI effect) or an external MIDI
loopback and log it; the Monitor shows messages and may be the simplest read-back.

**B0. Defaults and ranges.** Done for the 16 controls (Live 12.4.6 dump and saved set, Controls
and `.als` import). Still open: the CC Type list (is 119 the last entry; where do the non-CC
types sit) and how a chosen type is stored, read by saving a set with Custom B set to a few
types (CC 1, 119, the last entry).

**B1. Message mapping.** For each fixed control and for Custom B with CC Types 1, 7, 64, 74, 119
and a high one: set the value to 0, 1, 64, 127 (Pitch Bend: ends and centre) by automation in
the Arrangement (automation envelopes of the control) and read the output messages: type,
number, value, channel, timing.

**B2. Custom A.** On / off by automation with CC Type 64 and then with CC Type 1 and 7: values
sent. Compare Custom A with a dial.

**B3. Send.** Press Send (UI, once) with controls set to distinct values: the list, order and
timing of the 16 messages; with controls at their defaults; with Custom A off.

**B4. Initial value behaviour.** Load the set with the device on a track playing a looped clip
and read what is sent at load and at the first loop start.

**B5. Merge.** A clip with a Mod Wheel envelope (CC 1) running 0 to 127 over 4 bars, and the
device's Mod Wheel automated to a constant 64, then moving; read the combined stream.

**B6. Learn.** Learn on, a selected Custom control, a controller (or the harness's MIDI input)
sending CC 74 value 100: the new CC Type, the control's value, and whether the CC reaches the
output. Repeat with the control unselected and with two CCs in a row.

**B7. Pass-through.** A clip with notes, CC 1, CC 7, pitch bend and pressure through the device
with all controls left alone; the output has the same events (common.md C7).

**B8. Timing.** A ramp of one control from 0 to 127 over 1 bar: number of messages and their
times (one per integer value?). Fast and slow ramps; duplicates.

## Measured

Recorded from Live 12.4.6, runs `cc-control-static` and `-steps` (`devices/30.02-cc-control/`):
the fixed controls and Custom A, B and M stepped through 0, 1, 64, 127 (Pitch Bend −64, 0, 64; Custom A
off, on) by clip automation under a clip of 16 notes, and a static set of values. The notes come from
`midi_set.py read`; the controller messages are in the recorded clips' envelopes and were read from a
set saved after the recording (a recorder
track's `MidiClip` › `Envelopes` › `ClipEnvelope`, whose target `ControllerTargets.N` names the
message) [measured 12.4.6]:

- **Notes** equal the input in every case, so the device does not touch notes.
- **Mod Wheel** is CC 1 (`ControllerTargets.3`): the steps 1, 64, 127, 0 came out as the same values at
  the same beats (each a step at the automation point).
- **Pressure** is channel pressure (`ControllerTargets.1`): 1, 64, 127, 0 came out unchanged.
- **Pitch Bend** (`ControllerTargets.0`): the control's −64, 0, +64 came out as 14-bit values −8192,
  −0.5 and 8191 (the middle is half a step below 0, as Live's pitch bend envelope stores it). The control
  range −64 … 64 maps to the full bend range.
- **Custom A** is CC 64, the sustain pedal (`ControllerTargets.66`): Off sent 0 and On sent 127.
- **Custom B … M** of a fresh device have the CC Type 0 (`CustomFloatTargets` = 0) and sent nothing when
  stepped: no envelope was recorded for Custom B or Custom M.
- **A set value that nobody moves** sends nothing: a take starting with Mod Wheel 64, Pitch Bend 32,
  Pressure 100, Custom A on and Custom B 90 recorded no controller data (the values are stored state
  only). The first message is sent at the first change.

Not measured: other CC Types for Custom B … M, Send and Learn (buttons), a clip's own Mod Wheel
envelope together with the device's, very fast ramps, the device's output channel.

## Implementation notes

- **Structure.** A parameter-change listener turns a changed value into one event at the
  sample offset of the change (automation: at its breakpoint rate), a cache of the last sent
  value per message avoids duplicates, Send flushes all 16, Learn is a flag that watches the
  input event list. Incoming events are appended to the output list after the generated ones
  (the order at the same sample is [measure]).
- **Parameters.** Sixteen: three fixed (Mod Wheel, Pitch Bend, Pressure) and thirteen custom
  (Custom A as a boolean, Custom B to M as 0 – 127 steps), each custom with an assignable
  controller number and a name (strings are state, not automatable parameters). Ids never
  change once merged (AGENTS.md); the page toggles are view state.
- **Pitch bend** needs a 14-bit value; a 7-bit control can be mapped to ±8192.
- **MPE.** Not involved; the device sends channel messages on the track's channel.
- **UI only (can wait):** the two pages, Push labels, naming.
- **Prior art.** None needed. Max for Live CC-sender devices are common but this device is a
  trivial event generator.
- **`.als` import.** The device element is `MidiCcControl` [als 12.4.6]. (The probe read the
  device's `class_name` as `0` through the Live API, unlike every other device; the element
  name is the saved set's.) Parameter elements, in stored order [als 12.4.6]: `On`, `ModWheel`
  (0 – 127), `PitchBend` (−64 – 64), `Pressure` (0 – 127), `CustomBoolValue` (Custom A, bool),
  `CustomFloatValues.0` … `CustomFloatValues.11` (Custom B … M, 0 – 127). Values are stored as
  the API shows them. Not parameters, also stored [als 12.4.6]: `CustomBoolName` and
  `CustomFloatNames.0` … `.11` (the names, "Custom A" … "Custom M" in a fresh device),
  `CustomBoolTarget` (Custom A's CC Type, 64) and `CustomFloatTargets.0` … `.11` (the dials' CC
  Types, 0 in a fresh device). Whether a Target is the CC number itself or an index into the CC
  Type list is [measure] (B0). The page choice is not stored as an element of the device.
