# Looper (manual 29.25)

**Family:** delay and looping
**Note status:** dump checked, partly measured (remaining runs, [Measured](#measured))

## Summary

A real-time looping device in the style of hardware loopers. It records incoming audio, plays it
back as a loop that is quantised to the set, and layers further audio on top (overdub). It can
follow or set the song tempo, start and stop the song, change the loop speed (and so pitch),
reverse it, double or halve its length, and send its content out as a new clip [manual].

## Signal flow

```text
in ──► [input monitor switch: Input → Output] ───────────────────────────────────┐
 │                                                                               ▼
 └─► (record / overdub write: new = in + Feedback × old, during Overdub) ─► loop buffer ─► [Speed, Reverse] ─► (+) ─► out
                                          ▲                                    │
                                          └────── buffer read (loop playback) ◄─┘
```

- State machine: empty → Record → Play ⇄ Overdub → Stop; Clear and Undo/Redo act on the buffer
  [manual].
- Feedback applies only while overdubbing [manual].
- Speed, Reverse, ×2, ÷2 and the octave buttons act on playback of the buffer [manual].
- Looper can be an internal routing source or target, so its output can go through other tracks and
  back into it [manual, 29.25.1].

### Context menu and hidden options

- The transport buttons and several controls are MIDI-mappable; the multi-purpose button is
  meant for a footswitch [manual].
- Clip-style behaviour: launch quantisation (above) [manual].
- The API (Live 12 Max for Live) exposes: record, overdub, play, stop, undo, clear, double and
  half speed, double and half length, `record_length_index` and list, `overdub_after_record`,

## Behaviour

- **Maximum length.** In tests on a 120 BPM song, Looper stopped recording at about 47.5 – 48
  bars (about 90 – 96 seconds) [source: 2]. The exact limit as a function of sample rate and
  tempo is [measure].
- **Record and overdub.** Record overwrites; Overdub adds the new input over the existing buffer,
  with the old signal scaled by Feedback each pass [manual]. The first take sets the loop length
  (rounded to the grid when the song runs and the Quantization is set) [manual].
- **Layers and undo.** Undo removes the layer recorded since the last time Overdub was turned
  on (one level), then Redo restores it [manual]. So the buffer or a second buffer must hold the
  last overdub pass separately; with Feedback below 100 % the old layers are attenuated, so
  undo is probably a stored copy of the pre-overdub buffer [inferred].
- **Tempo.** Looper stores the tempo at which the loop was recorded (read by the API) [source: 3].
  Follow modes resample playback so the loop plays at the song tempo [manual]. Set modes change
  the song tempo to the recording's [manual]. For free recording with the song stopped the tempo
  is guessed, with possible octave errors [manual]; the method is [measure].
- **Speed and pitch.** Speed changes resample the playback: speed and pitch change together
  [manual]. The octave buttons double or halve it [manual]; the knob is in semitones (Measured › Fifth set).
  Overdubbing at non-unity speed: the new material is recorded in a way that returns to normal
  pitch when played at normal speed [inferred; measure].
- **Reverse.** The state at the time of recording decides the direction for each layer, so
  layers recorded while reversed play forward when Reverse is turned off, and vice versa
  [manual]. This requires per-layer direction handling, so each layer or each recording pass
  stays separate in memory [inferred].
- **Quantised actions.** While the transport runs, transport buttons, the octave buttons and
  Reverse act on the next quantisation boundary [manual].
- **Song Control.** Looper can start or stop the global transport [manual].
- **Monitoring.** The Input -> Output chooser controls the dry path as in the table [manual].
- **Dry path.** There is no Dry/Wet; Looper outputs its loop, plus the monitored input
  [manual, inferred].

## Edge cases

- Clear while overdubbing with the transport running keeps length and tempo; otherwise it resets
  them [manual].
- Fixed Record Length with the song stopped: the song tempo is changed to fit (when Tempo
  Control sets it) [manual].
- Feedback changes take effect at the next loop repetition, not mid-pass [manual]; a Feedback lane stepped mid-pass acts from the sample of the step [measured 12.4.7] (Measured › Fifth set).
- Reverse on empty buffer: no effect [inferred].
- Maximum length reached while recording: the device stops or switches state [source: 2];
  which state is [measure].
- ×2 and ÷2 while overdubbing or reversed: [measure].
- Drag a file onto "Drag me!" while playing: contents replaced; tempo and length from the file
  [manual; measure].
- Export while recording is not allowed [source: 3].
- Looper in a return track with Input -> Output Never [manual].
- Sample-rate change: buffer length in seconds fixed; loop length in samples changes
  [inferred].

## Measured

[measured 12.4.6] Behaviour run at 44.1 kHz in Live 12.4.6 (`devices/29.25-looper/`: `looper-monitor-states`, in the remaining set; `looper-state-lane` in the third set, rendered by Live 12.4.7: Measured › Third set), the device with the State and the Input -> Output choice stored from the first sample, the 1 kHz staircase and the impulse; the first measurement of this device. These are observations, not a model.

| State | Input -> Output | output |
|---|---|---|
| Stop | Never | silent (-240 dB) |
| Stop | Rec/OVR | silent |
| Stop | Rec/OVR/Stop | the input, 0.0 dB, impulse at 0 ms |
| Record | Never | silent |
| Record | Rec/OVR | silent |
| Play | Rec/OVR | silent |
| Play | Rec/OVR/Stop | the input, 0.0 dB |
| Overdub | Rec/OVR/Stop | the input, 0.0 dB |
| default (Stop, Always) | | the input, 0.0 dB |

- **The input is passed unchanged (0.0 dB, no delay) exactly when Input -> Output is Always or Rec/OVR/Stop and the device is stopped; Never and Rec/OVR leave the stopped device silent**, as the chooser's names say [measured 12.4.6].
- **A State stored in the set does not start the device**: the eight cases fit the device being stopped in every one of them (Record with Rec/OVR would pass the input if it were recording, Play and Overdub with Rec/OVR/Stop pass it only because Overdub and Stop both do), nothing was recorded and nothing played back, and there is no noise in the silence. A recording needs a transport action during playback, which the saved set cannot supply [measured 12.4.6; the reading that the state did not take effect is inferred from the pattern].
### Third set (Live 12.4.7)

[measured 12.4.7] Behaviour run at 44.1 kHz in Live 12.4.7 (`looper-state-lane`), Input -> Output Always, Quantization, Tempo Control and Song Control None, State moved by a lane, the probe with a 0.5 s impulse at 0.5 s. The second case is the one the six-run pilot could not read (see below).

| Lane (beat: State) | loop length | what comes out after the last change |
|---|---|---|
| 0: Stop, 0.5: Record, 4: Play | 1.75 s | the recorded signal, again every 1.75 s, at 0.95 of the input |
| 0: Stop, 0.5: Record, 4: Overdub, 8: Play | 1.75 s | the first take at 0.42, plus the input played during the Overdub pass at 1.0 |

- **A State lane starts the device; the stored State alone does not.** Moving State to Record at beat 0.5 and to Play at beat 4 records exactly the input between the two changes (0.25 s to 2.0 s, 1.75 s, which is 3.5 beats at 120 BPM) and then repeats it without a gap: the impulse recorded 0.25 s into the take comes back at 2.25 s and every 1.75 s after that to the end of the render (26 repeats checked, all at 0.00 ms), and what was recorded matches the input again and again to within -75 dB of the repeat, so the loop is a plain sample-accurate copy [measured 12.4.7].
- **The playback is 0.95 of the recorded input (-0.44 dB), the same on every pass.** The impulse of 0.501 comes back at 0.476 on all 26 repeats and the whole take is scaled by that one factor (least-squares gain 0.9500). A constant factor on every pass is not the Feedback decay, and Feedback is left at its default of 100 % [dump 12.4.6]. The 0.95 is the centre tap of a fixed low-pass that every write of the loop passes through (Measured › Fifth set): a tone at 1 kHz comes back at 1.0000, white noise at 0.947 and an impulse at 0.950; it is the same at Input -> Output Never and Always [measured 12.4.7].
- **The input is still heard while the loop plays** (Input -> Output Always): the output minus the bypass render holds only the loop, so the input and the loop add [measured 12.4.7].
- **Overdub adds the input at unity and scales the old take.** Once the Overdub pass has ended (State Play from beat 8), the loop holds the input of the Overdub pass (2.0 s to 3.75 s, mapped to loop positions 0 to 1.75 s, at gain 1.0, residual below -150 dB for the segments away from the take's own content) plus the first take at 0.42 of the recorded level, a factor that stays constant on every later repeat. The Overdub pass lasted 2.0 s, 1.14 loops, so the first 0.25 s of the loop were written twice (the input at 3.75 s to 4.0 s sits in the first 0.25 s of the loop on top of the first pass's input) [measured 12.4.7].
- **The factor 0.42 is not Feedback 100 %.** With Feedback at its default of 100 % the manual says old material is never lowered [manual]; the observed 0.42 (-7.6 dB) after one to two Overdub passes is much lower. The fifth set found Feedback 100 % leaving the old layer at exactly 1.0 over the passes (apart from the low-pass, whose centre tap after three writes is still 0.87), so the 0.42 is not a Feedback factor. The Overdub pass ended at 4.0 s, which is loop position 0.25 s, where the take's impulse sits, and the Overdub to Play change is a crossfade about 5 ms long, so the impulse was most probably read in the middle of that crossfade; the impulse reads 0.476 at 2.25 s, 0.438 at 4.0 s (mid-change) and 0.209 from 5.75 s. This reading is inferred, not re-rendered [inferred].
- **Pilot at 88.2 kHz.** The pilot's version of the same two cases (rendered at 88.2 kHz and brought to 44.1 kHz) is bit-identical to the bypass render in both cases: the Looper did not start. The same lane at 44.1 kHz in the third set works, so the difference is the sample rate or the pilot's set, and the sample rate as the cause is inferred; a Looper State lane is worth rendering at 44.1 kHz only [measured 12.4.7].

### Fifth set (Live 12.4.7)

[measured 12.4.7] Behaviour runs at 44.1 kHz in Live 12.4.7 (`looper-feedback-noise`, `looper-speed-reverse`), Quantization, Tempo Control and Song Control None. The State lane runs Stop, Record, Overdub and Play; the loop is read in the silence after the probe's noise (the loop of the steady 1 s of noise, played from 42.875 s) by a least-squares fit on the input noise of each earlier pass, in 50 ms windows along the loop. The coefficients are those below 4 kHz unless a band is named, because every write also filters (below). These are observations, not a model.

**Feedback** (Record 30.875 s, Overdub 31.875 s to 33.875 s = two 1 s passes, then Play; coefficient of each layer in the loop, oldest first):

| Feedback | take | pass 1 | pass 2 |
|---|---|---|---|
| 100 % | 1.000 | 1.000 | 1.000 |
| 75 % | 0.563 | 0.750 | 1.000 |
| 50 % | 0.250 | 0.500 | 1.000 |
| 25 % | 0.063 | 0.250 | 1.000 |
| 0 % | 0 | 0 | 1.000 |

- **Feedback is a plain linear gain on the old layer, applied once per Overdub pass, and the input is written at 1.0.** Each entry is Feedback to the power of the passes since the layer was written (0.75^2 = 0.5625, 0.5^2 = 0.25, 0.25^2 = 0.0625) to three decimals. Input -> Output Never and Always give the same loop (the recording and the overdub do not depend on the monitoring) [measured 12.4.7].
- **A Feedback lane acts at the sample of its step.** With the lane 100 % until beat 64.5 (0.375 s into the first Overdub pass) and 25 % after, the take reads 0.25 before loop position 0.375 s and 0.0625 after it (the transition lies in the 0.35 to 0.40 s window), and pass 1 reads 0.25 everywhere (it is scaled once, by the second pass at 25 %): the first pass was at 100 % up to the step and at 25 % after it. The manual's "from the next repetition" does not hold for a lane [measured 12.4.7].
- **Every write passes through a fixed low-pass, so the old layers lose treble on each pass even at Feedback 100 %.** The gain of one write is flat to 10 kHz (1.000 at 8 to 10 kHz, 0.997 at 12 kHz), 0.983 at 14 kHz, 0.942 at 16 kHz, 0.868 at 18 kHz, 0.789 at 20 kHz and 0.763 at 21 kHz, with zero phase: a symmetric filter whose centre tap is 0.950 (the neighbouring taps, from the transfer function, are 0.0442, -0.0304, 0.0159) [measured 12.4.7]. The recording is one write and each Overdub pass writes the old content again, so after three writes the centre tap is 0.875 and the 18 to 20 kHz band is 0.68, 0.47 and 0.39 in the three layers of the Feedback 100 % loop. A 1 kHz tone is unaffected (gain 1.0000 on every Speed). Only 44.1 kHz was rendered, so whether the corner scales with the sample rate is not known [measured 12.4.7].
- **Playback starts at the sample of the change.** The first output of a Play after a Record is at 5.75002 s for a Play at 5.75 s (one sample late) [measured 12.4.7].
- **Fades at the edges are short.** The last 4 to 5 ms of the loop fade out: the coefficient of the input at that position falls from 0.95 to about 0 between 5 and 1 ms before the wrap, and the output level dips to 0.66 of its neighbours there, as a linear crossfade into uncorrelated material gives (0.71). The best second source is the input about 6 ms before the take (weight 0.37), but this is not a clean fit and the partner is not identified. The start of the loop has no fade-in. An Overdub to Play change at loop position 0.25 s switches from the newer layer to the older one over about 5 ms (the newer layer's coefficient falls from 0.90 at 248 ms to 0.74, 0.39 and 0.02 at 250, 252 and 254 ms while the older layer's rises from 0 to 0.77 at 254 ms) [measured 12.4.7].

**Speed and Reverse** (`looper-speed-reverse`, Feedback 100 %, Input -> Output Never):

| Speed | 1 kHz tone, 1 s loop | gain |
|---|---|---|
| 0 | 1000.0 Hz | 1.0000 |
| +12 | 2000.0 Hz | 1.0000 |
| -12 | 500.0 Hz | 1.0000 |
| +7 | 1498.27 Hz | 1.0000 |
| +24 | 4000.0 Hz | 1.0000 |
| -24 | 250.0 Hz | 1.0000 |

- **Speed is in semitones, exactly 2^(Speed / 12).** The six values give the ratios of equal temperament to 0.01 Hz (1498.27 Hz at +7 is 1000 x 2^(7/12)) and the level does not change [measured 12.4.7].
- **Reverse plays the loop backwards from the Play change.** The 3 s recording of the sweep (33 Hz to 3.9 kHz, rising) comes back falling, 5.0 kHz at the start of the loop to 43 Hz at the end, and starts again every 3 s; forward it comes back rising from 33 Hz and restarts every 3 s (8.75 s) [measured 12.4.7]. How Reverse treats layers overdubbed before or after the switch is not read.

## Implementation notes

- **Not a normal `Device`.** Looper needs transport integration: quantised actions, setting the
  song tempo, starting and stopping the song, exporting a clip. These must be commands
  in the engine or session that the UI and other controllers also use, not hidden in a device's `process`; the DSP part is a
  loop buffer with multi-layer overdub, resampling playback and reverse.
- **Building blocks:** parameter smoothing and dB conversions; a tempo detector for the
  free-recording guess.
- **Also needed:** pre-allocated loop memory (allocated outside the audio callback, up to the
  maximum length), layer storage for undo and reverse, a resampling read with interpolation, a
  quantisation scheduler tied to the transport, a clip export path (a command), MIDI-footswitch
  mapping.
- **Hard to match:** how layers are stored for Reverse and Undo, the tempo guess, behaviour at the
  length limit.
- **.als element name:** `Looper` [als 12.4.6]. Parameter elements in the set saved from Live 12.4.6
  [als 12.4.6], each holding a `Manual` value: `On` (bool), `State` (index 0 – 3), `Feedback`
  (fraction, 1 = 100 %), `Reverse` (bool), `Monitor` (index 0 – 3), `Pitch` (the Speed control, 0),
  `LocalQuantization` (index 0 – 14), `SongControl` (index 0 – 2) and `TempoControl` (index 0 – 2).
  The stepped controls are stored as indices. Not parameters but plain values on the device element [als 12.4.6]: `FixedLengthRecord` (Record Length,
  an index, 10), `OverdubAfterRecord` (true = Overdub), `MappablePedal` (false), `ExportCounter` (1), and
  `SavedSampleRate`, `SavedChannelCount`, `SavedTempo`, `SavedLengthInFrames`, `SavedLengthInBeats` (all −1
  with an empty buffer; they probably describe a saved recording [inferred]). Where the recorded audio
  itself is stored is [measure].
