# External Audio Effect (manual 29.18)

**Family:** analysis and utility
**Note status:** dump checked

## Summary

A send-and-return device for hardware effects. It does not process the sound itself: it sends the
signal arriving at the device out of chosen audio-interface outputs, takes the processed signal back
from chosen inputs, mixes it with the dry signal and compensates for the round-trip latency of the
hardware with a manually set delay [manual].

## Signal flow

Shared parts: [common.md](common.md) (title bar only; no side-chain).

```text
                          ┌─► Gain (to) ─► Audio To ─► [hardware effect] ─► Audio From ─► Gain (from) ─► Invert ─┐
input ─┬─(sent signal)────┘                                                                                      ├─► Dry/Wet ─► out
       └─► [dry path delayed by Hardware Latency] ──────────────────────────────────────────────────────────────┘
Peak indicators: one on the send, one on the return [manual]
```

- One gain knob sets the send level to the hardware, the other the level of the returning signal [manual].
- Invert flips the phase of the returned signal only [manual].
- The dry path must be delayed by the same amount as the hardware's round trip for Dry/Wet to be
  phase-aligned; the delay is the Hardware Latency setting [inferred]. How the compensation is
  implemented (a delay on the dry path and a latency report to the host, so other tracks are
  aligned) is [inferred]; the manual says only that the slider compensates delays Live cannot detect
  [manual].
- Dry/Wet at 100 % is advised in a return track [manual].
- Whether the Peak indicators read before or after their Gain knob is [measure].

### Context menu and hidden options

None are described in the manual. The choosers' "Configure…" entries open the audio preferences
[manual]. Live's Delay Compensation option (Options menu, a host setting) disables the latency
slider [manual].

## Behaviour

- **Routing.** The send takes the signal at the device's position in the chain; a stereo chain
  sent to a mono output is summed (whether with a level change is [measure], a forum poster asked
  whether it is reduced by 3 dB [source: 2], unanswered there). The return is read from the chosen
  inputs; their channel count decides mono or stereo [inferred].
- **Gain.** Two level controls; "set carefully to avoid clipping" in the hardware and on return
  [manual].
- **Peak indicators.** Hold the highest level seen until clicked [manual]; their scale is dB peak
  [inferred], range [measure].
- **Invert.** Polarity inversion of the return [manual].
- **Dry/Wet.** The balance between dry and returned signals [manual]; whether the dry path is delayed
  by the Hardware Latency amount is [inferred]; law [measure].
- **Hardware Latency.** A delay in milliseconds or samples set by the user, which makes the
  device's reported latency larger so Live aligns the track with the others. In samples the value is
  constant when the sample rate changes; in milliseconds the time is kept [manual]. With monitoring on,
  automatic compensation does not work (use direct monitoring) [source: 3]. The range and the exact
  effect (does the slider delay the dry only, or does it report latency so Live shifts the whole
  track earlier) are [measure].
- **Delay Compensation off:** the slider is disabled [manual].
- **No recording button:** the device has no record button; to capture the returned signal, route
  the track's output to another audio track [source: 3] (about the host, not the device).
- **Latency on the host side:** the audio I/O round trip is the driver's input plus output buffers.

## Edge cases

- **No outputs or inputs chosen:** the device passes the dry signal or silence on the wet path
  [measure].
- **Same interface output and input (a loopback):** feedback if the hardware is routed back;
  the manual only warns about level [manual].
- **Dry/Wet 100 % on a track:** the track carries only the returned signal [inferred].
- **Latency set wrong:** a comb filter between wet and dry at partial Dry/Wet [inferred].
- **Sample rate change:** milliseconds are kept in ms mode, samples in samples mode [manual].
- **Offline render or freeze:** the hardware cannot be run faster than real time; how Live renders a
  track with this device (it records in real time, or leaves the wet path silent) is [measure].
- **Interface buffer size:** compensation is less reliable with large buffers; one user found
  it reliable at a 64-sample buffer [source: 3].

## Implementation notes

- **Needs:** a multi-channel interface routing layer (named output and input channel pairs for each
  external effect), a send/return transport through the real-time path that stays real-time safe (lock-free
  queues, no blocking: the returned audio arrives at the next block or later, so a round trip has
  a minimum latency of the driver's input plus output buffers), a delay line for the dry path, the
  host's delay compensation reporting for a device with a user-set latency, peak meters with click
  reset, and the "Configure…" shortcut into the audio settings. Also offline-render policy (the
  hardware cannot be rendered offline).
- **`.als` element:** `ProxyAudioEffectDevice` [als 12.4.6]. Parameter elements in the set saved from
  Live 12.4.6 [als 12.4.6], each holding a `Manual` value: `On` (bool), `OutputHelper/Volume` and
  `InputHelper/Volume` (linear gain, 1 = 0 dB; the loaded value is 1; the names suggest the
  `Output Gain` and `Input Gain` parameters respectively), and `DryWet` (fraction, 1 = 100 %). The
  choosers, Invert and Hardware Latency are not among the parameters; where they are stored is
  [measure].
